.NET observability with ADOT auto-instrumentation and CloudWatch Application Signals

Telemetry added at startup by configuration, then turned into service health, maps, and SLOs

Architecture

Application Signals data (spans + computed metrics) Traces Business metrics (OTLP) Logs (Serilog JSON with trace IDs)

ADOT Where ADOT comes in

  1. At launch, not in code. Environment variables tell the .NET runtime to load the ADOT auto-instrumentation before the application starts. The same variables are set by a launch script, a Windows service, or an ECS task definition.
  2. Instruments common libraries automatically. Incoming requests, outgoing HTTP calls, AWS SDK calls, and .NET runtime health become spans and metrics.
  3. Listens to your existing telemetry. Business spans and metrics written with .NET's built-in ActivitySource and Meter are picked up by name. That code is identical to the manual-SDK version.
  4. Adds the AWS layer. The ADOT plugin tags each span with service, operation, and dependency, and computes Application Signals metrics from them.

App Signals What Application Signals adds

  • A service-level view without dashboards to build: volume, latency, errors, and faults per service and per operation.
  • Dependencies: how the storefront, the API, and AWS services call each other, with health on each edge.
  • SLOs: define targets such as checkout success and latency, and alarm on them.
  • Pivots: from an unhealthy operation to example traces in AWS X-Ray and the matching logs in CloudWatch Logs.
  • Business context stays: custom metrics still land in their own namespace alongside the standard signals.

Many customers combine the two: auto-instrumentation for broad coverage, and a small amount of custom instrumentation where business context matters. Customers can choose based on how much control they need. See the Amazon CloudWatch Application Signals documentation.
