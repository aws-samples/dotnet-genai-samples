Observability for .NET applications on AWS with OpenTelemetry

How traces, metrics, and logs flow from a .NET application into Amazon CloudWatch

High-level architecture

Traces (OTLP) Metrics (OTLP) Logs (structured JSON with trace context)

Talk track

  1. Instrument once, in standard form. The OpenTelemetry .NET SDK captures incoming requests, outgoing HTTP calls, AWS SDK calls, and .NET runtime health, with no vendor-specific code in the application.
  2. Add business context. A custom ActivitySource and Meter add spans like checkout and payment, and metrics like orders placed and checkout failures.
  3. Export over OTLP to a local agent. Traces and metrics leave the process over OTLP to an agent running next to the app. The app holds no AWS credentials for telemetry; the agent uses the task or instance role.
  4. Logs carry the trace. Every structured log line includes the trace ID and span ID, so CloudWatch can link logs to the request that produced them.
  5. Land in Amazon CloudWatch. Traces go to AWS X-Ray, metrics to CloudWatch Metrics, and logs to CloudWatch Logs, all correlated by trace ID.
  6. Same code everywhere. The same application code runs locally, on Amazon EC2, Amazon ECS, or Amazon EKS. Only the agent deployment and log shipping change.

Design choices to discuss

  • Why an agent instead of exporting directly? It keeps exporters and credentials out of the app, batches and retries outside the request path, and lets teams change destinations without redeploying code.
  • Logs as JSON vs. OTLP. This design writes logs as structured JSON so existing log pipelines and Logs Insights queries keep working. Sending logs over OTLP through a collector is another option. Customers can choose based on their existing tooling.
  • CloudWatch agent vs. ADOT collector. Both accept OTLP. Consider the CloudWatch agent for a simpler, CloudWatch-focused setup, and the ADOT collector when you need custom processing or multiple destinations.
  • Manual SDK vs. auto-instrumentation. The SDK gives full control over spans and metrics. AWS also offers .NET auto-instrumentation with CloudWatch Application Signals for teams that want less code.
  • Async boundaries. Trace context travels in queue message attributes, so the fulfillment worker continues the same trace as the checkout that triggered it.
