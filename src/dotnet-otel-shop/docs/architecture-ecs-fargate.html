Deployment 2: Amazon ECS on AWS Fargate

CloudWatch agent as a sidecar container in every task; Serilog writes JSON to stdout for the container log driver

Overview · Deployment 1: Laptop / EC2 · Deployment 2: Amazon ECS on AWS Fargate

Architecture

Traces (OTLP)Metrics (OTLP)Logs (Serilog → stdout → log driver)

Talk track

  1. Agent as a sidecar: the task definition adds a CloudWatch agent container next to each application container. They share localhost, so the app's OTLP setup is identical to the laptop and EC2.
  2. Traces and metrics: the OpenTelemetry .NET SDK exports over OTLP to the sidecar, which forwards to AWS X-Ray and CloudWatch Metrics using the task IAM role.
  3. Logs: Serilog still adds trace and span IDs and formats JSON, but writes to stdout instead of a file. Files inside a container are lost when the task stops.
  4. Log delivery: the awslogs log driver, provided by Amazon ECS, ships stdout to CloudWatch Logs. No agent needs to tail files.
  5. Platform metrics: Container Insights adds task-level CPU, memory, and network next to the application metrics.

Design choices to discuss

  • Sidecar vs. shared agent: AWS Fargate has no host to install an agent on, so the sidecar pattern places one agent with each task and scales with it.
  • stdout vs. file tailing: stdout with the container log driver is the common container pattern. Customers who prefer the agent to collect logs can evaluate a shared task volume for the log file, or AWS FireLens for routing and filtering.
  • Agent choice: the CloudWatch agent and the AWS Distro for OpenTelemetry (ADOT) collector both run as sidecars and accept OTLP. Customers can choose based on how much custom processing they need.
  • Lower-code option: CloudWatch Application Signals with .NET auto-instrumentation is another approach for teams that want less SDK code.
